# 抽样统计虚拟仿真系统 - 数据库设计思路 V2.0

## 文档说明

- **项目名称**：抽样统计虚拟仿真教学系统
- **版本**：V2.0（优化版）
- **基于版本**：V1.0 原设计
- **文档目的**：在原有设计基础上进行优化，解决功能需求与数据模型的差距

---

## 一、优化概述

### 1.1 本次优化内容

| 序号 | 优化项 | 原设计问题 | 优化方案 |
|------|--------|------------|----------|
| 1 | 登录日志 | 无法记录登录历史和最后登录时间 | 新增 `login_log` 表 |
| 2 | 公告已读 | 无法追踪用户是否已读公告 | 新增 `announcement_read` 表 |
| 3 | 用户状态 | 教师/助教无法停用 | 为 `teacher`、`assistant` 添加 `status` 字段 |
| 4 | 管理员改密 | 管理员无首次登录改密机制 | 为 `admin` 添加 `is_first_login` 字段 |
| 5 | 系统监控 | 无监控数据持久化 | 新增 `system_metrics` 表 |
| 6 | 操作日志 | 关键操作无审计追踪 | 新增 `operation_log` 表 |
| 7 | 批改草稿 | 批改中途无法保存 | `submission` 增加草稿状态 |
| 8 | 存储优化 | 抽样结果 JSON 可能过大 | 增加 `sampling_data_path` 字段，大数据存文件 |

### 1.2 设计原则（保持不变）

| 原则 | 说明 |
|------|------|
| 简洁优先 | MVP阶段优先保证功能完整，避免过度设计 |
| 数据完整性 | 通过外键约束保证关联数据的一致性 |
| 查询效率 | 为高频查询字段建立索引 |
| 可扩展性 | 使用JSON字段存储结构化但可能变化的数据 |
| 软删除 | 关键业务数据采用软删除，避免误操作导致数据丢失 |

## 二、表结构变更详细说明

### 2.1 用户域变更

#### admin（管理员表）—— 新增字段

| 新增字段 | 类型 | 说明 |
|----------|------|------|
| is_first_login | TINYINT(1) | 是否首次登录，默认1，改密后置0 |

**变更理由**：统一所有角色的首次登录改密机制，增强安全性。

#### teacher（教师表）—— 新增字段

| 新增字段 | 类型 | 说明 |
|----------|------|------|
| status | TINYINT | 账号状态：1-正常，0-停用 |

**变更理由**：支持管理员停用教师账号（如离职、休假等场景）。

#### assistant（助教表）—— 新增字段

| 新增字段 | 类型 | 说明 |
|----------|------|------|
| status | TINYINT | 账号状态：1-正常，0-停用 |

**变更理由**：与教师表保持一致，支持账号管理。

### 2.2 新增表

#### login_log（登录日志表）

记录所有用户的登录历史，支持：
- 显示「最后登录时间」
- 统计「今日登录次数」
- 安全审计

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | BIGINT | 是 | 主键 |
| user_type | TINYINT | 是 | 用户类型：1-管理员，2-教师，3-助教，4-学生 |
| user_id | BIGINT | 是 | 用户ID |
| login_at | DATETIME | 是 | 登录时间 |
| ip_address | VARCHAR(45) | 否 | 登录IP（支持IPv6） |
| user_agent | VARCHAR(500) | 否 | 浏览器/客户端信息 |

**索引设计**：
- `idx_user`：(user_type, user_id) - 查询用户登录历史
- `idx_login_at`：(login_at) - 按时间统计

**查询示例**：
```sql
-- 获取用户最后登录时间
SELECT MAX(login_at) FROM login_log WHERE user_type = 4 AND user_id = 123;

-- 统计今日登录次数
SELECT COUNT(*) FROM login_log WHERE DATE(login_at) = CURDATE();
```

#### announcement_read（公告已读表）

追踪用户是否已读公告，支持：
- 区分「未读公告」和「已读公告」
- 只显示未读公告提醒

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | BIGINT | 是 | 主键 |
| announcement_id | BIGINT | 是 | 公告ID |
| user_type | TINYINT | 是 | 用户类型 |
| user_id | BIGINT | 是 | 用户ID |
| read_at | DATETIME | 是 | 阅读时间 |

**约束**：
- 联合唯一索引 (announcement_id, user_type, user_id)

**查询示例**：
```sql
-- 获取学生未读公告
SELECT a.* FROM announcement a
WHERE a.status = 1
AND NOT EXISTS (
    SELECT 1 FROM announcement_read ar 
    WHERE ar.announcement_id = a.id 
    AND ar.user_type = 4 
    AND ar.user_id = 123
);
```

#### system_metrics（系统监控数据表）

持久化存储系统监控指标，支持：
- 历史趋势图展示
- 阈值告警

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | BIGINT | 是 | 主键 |
| metric_type | VARCHAR(50) | 是 | 指标类型：cpu, memory, disk 等 |
| metric_value | DECIMAL(10,2) | 是 | 指标值 |
| recorded_at | DATETIME | 是 | 记录时间 |

**索引设计**：
- `idx_type_time`：(metric_type, recorded_at) - 按类型和时间查询

**数据采集策略**：
- 每分钟采集一次
- 保留最近30天数据
- 可配置定期清理任务

#### operation_log（操作日志表）

记录关键业务操作，用于审计和问题排查：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | BIGINT | 是 | 主键 |
| user_type | TINYINT | 是 | 操作者类型 |
| user_id | BIGINT | 是 | 操作者ID |
| action | VARCHAR(100) | 是 | 操作类型 |
| target_type | VARCHAR(50) | 否 | 操作对象类型 |
| target_id | BIGINT | 否 | 操作对象ID |
| detail | JSON | 否 | 操作详情 |
| ip_address | VARCHAR(45) | 否 | 操作IP |
| created_at | DATETIME | 是 | 操作时间 |

**操作类型示例**：
- `TOPIC_CREATE` - 创建课题
- `TOPIC_PUBLISH` - 发布课题
- `TASK_PUBLISH` - 发布任务
- `SUBMISSION_GRADE` - 批改作业
- `SUBMISSION_REJECT` - 驳回作业
- `STUDENT_IMPORT` - 批量导入学生
- `PASSWORD_RESET` - 重置密码

### 2.3 现有表优化

#### experiment（实验记录表）

**新增字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| sampling_data_path | VARCHAR(500) | 抽样结果文件路径（大数据时使用） |

**优化说明**：

当抽样样本量较大时（如单次抽样超过500条），将 `sample_data` 存储为 JSON 文件而非数据库字段：

```
/data/sampling/
└── experiment_{id}/
    ├── simple_random.json
    ├── systematic.json
    └── stratified.json
```

`sampling_results` JSON 结构优化：
```json
{
  "simple_random": {
    "sample_count": 400,
    "sample_data": [...]      // 小数据量时内嵌
  },
  "systematic": {
    "k_value": 25,
    "sample_count": 400,
    "data_file": "systematic.json"  // 大数据量时引用文件
  }
}
```

**应用层逻辑**：
- 样本量 ≤ 500：直接存 JSON 字段
- 样本量 > 500：存文件，JSON 中只记录元数据

#### submission（提交记录表）

**状态值变更**：

| 原设计 | 新设计 |
|--------|--------|
| 1-待批改 | 0-批改草稿（新增） |
| 2-已批改 | 1-待批改 |
| 3-被驳回 | 2-已批改 |
| - | 3-被驳回 |

**变更理由**：支持批改中途保存草稿。

## 五、视图设计更新

### 5.1 新增视图

#### v_user_last_login（用户最后登录视图）

简化获取用户最后登录时间的查询：

```sql
CREATE VIEW v_user_last_login AS
SELECT 
    user_type,
    user_id,
    MAX(login_at) AS last_login_at
FROM login_log
GROUP BY user_type, user_id;
```

#### v_unread_announcement_count（未读公告统计视图）

统计各用户的未读公告数：

```sql
CREATE VIEW v_unread_announcement_count AS
SELECT 
    u.user_type,
    u.user_id,
    COUNT(a.id) AS unread_count
FROM (
    -- 所有活跃用户的笛卡尔积
    SELECT 1 AS user_type, id AS user_id FROM admin
    UNION ALL SELECT 2, id FROM teacher WHERE status = 1
    UNION ALL SELECT 3, id FROM assistant WHERE status = 1
    UNION ALL SELECT 4, id FROM student WHERE status = 1
) u
CROSS JOIN announcement a
LEFT JOIN announcement_read ar ON a.id = ar.announcement_id 
    AND ar.user_type = u.user_type 
    AND ar.user_id = u.user_id
WHERE a.status = 1 AND ar.id IS NULL
GROUP BY u.user_type, u.user_id;
```

- v_class_student_count

## 八、数据清理策略

### 8.1 日志表清理

为避免日志表无限增长，建议配置定期清理：

| 表 | 保留策略 | 清理方式 |
|------|----------|----------|
| login_log | 保留90天 | 定时任务删除 |
| system_metrics | 保留30天 | 定时任务删除 |
| operation_log | 保留365天 | 定时任务删除 |

### 8.2 清理SQL示例

```sql
-- 清理90天前的登录日志
DELETE FROM login_log WHERE login_at < DATE_SUB(NOW(), INTERVAL 90 DAY);

-- 清理30天前的监控数据
DELETE FROM system_metrics WHERE recorded_at < DATE_SUB(NOW(), INTERVAL 30 DAY);
```

## 十、总结

### 10.1 优化亮点

1. **完善的登录追踪**：支持最后登录时间显示和登录统计
2. **公告已读机制**：精确追踪用户阅读状态
3. **统一的账号管理**：所有角色都支持状态控制
4. **系统监控持久化**：支持历史趋势分析
5. **操作审计日志**：关键操作可追溯
6. **存储优化**：大数据量抽样结果存文件

### 10.2 对开发的影响

| 模块 | 影响 |
|------|------|
| 登录 | 需在登录成功后写入 login_log |
| 公告 | 需在查看公告时写入 announcement_read |
| 批改 | submission status 增加草稿状态 |
| 抽样 | 需判断数据量决定存储方式 |
| 监控 | 需开发定时采集任务 |
