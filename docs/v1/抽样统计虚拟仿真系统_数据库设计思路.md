# 抽样统计虚拟仿真系统 - 数据库设计思路

## 文档说明

- **项目名称**：抽样统计虚拟仿真教学系统
- **版本**：V2.0
- **文档目的**：阐述数据库设计的整体思路、核心决策、表结构说明及字段设计依据，为开发和后期维护提供参考

---

## 一、设计原则

### 1.1 核心原则

| 原则 | 说明 |
|------|------|
| 简洁优先 | MVP阶段优先保证功能完整，避免过度设计 |
| 数据完整性 | 通过外键约束保证关联数据的一致性 |
| 查询效率 | 为高频查询字段建立索引 |
| 可扩展性 | 使用JSON字段存储结构化但可能变化的数据 |
| 软删除 | 关键业务数据采用软删除，避免误操作导致数据丢失 |

### 1.2 技术选型

| 项目 | 选择 | 理由 |
|------|------|------|
| 数据库 | MySQL 8.0+ | 成熟稳定，JSON支持完善，社区资源丰富 |
| 字符集 | utf8mb4 | 完整支持中文及emoji |
| 排序规则 | utf8mb4_general_ci | 大小写不敏感，适合一般业务场景 |
| 存储引擎 | InnoDB | 支持事务和外键约束 |

## 三、关键设计决策

### 3.1 用户表设计：分表 vs 合表

**决策：采用分表设计**

| 方案 | 优点 | 缺点 |
|------|------|------|
| 合表（单一user表） | 统一管理，登录逻辑简单 | 字段冗余，权限混乱 |
| 分表（四张用户表） | 字段清晰，权限分明 | 登录时需判断用户类型 |

**选择分表的理由：**

1. **字段差异大**
   - 学生有：学号、班级
   - 教师有：工号
   - 助教有：创建者教师ID
   - 管理员只需：账号密码

2. **权限模型不同**
   - 各角色的功能权限完全不同
   - 分表后代码逻辑更清晰

3. **避免空字段**
   - 合表会导致大量NULL值
   - 分表每个字段都有意义

**登录处理方案：**
- 前端提供角色选择（学生/教师/助教/管理员）
- 或通过账号格式自动识别（如学号纯数字、工号带字母前缀）

### 3.2 总体数据存储：数据库表 vs 文件

**决策：存储为文件**

| 方案 | 优点 | 缺点 |
|------|------|------|
| 存数据库（动态建表） | 可用SQL查询 | 表数量膨胀，管理复杂 |
| 存文件 | 简单，数据隔离 | 需要文件读写操作 |

**选择文件存储的理由：**

1. **数据特点**
   - 总体数据是只读的，上传后不再修改
   - 不需要复杂的SQL查询
   - 每个课题的数据结构不同（字段不固定）

2. **使用场景**
   - 抽样操作在应用层完成
   - 统计计算在内存中进行
   - 不需要跨课题联合查询

3. **实现方式**
   - Excel原文件存储在文件系统
   - 解析后可转为JSON或CSV便于读取
   - 文件路径记录在topic表的excel_file_path字段

### 3.3 抽样结果存储：明细表 vs JSON字段

**决策：使用JSON字段存储**

| 方案 | 优点 | 缺点 |
|------|------|------|
| 明细表 | 可精确查询每条样本 | 数据量巨大，表结构复杂 |
| JSON字段 | 简单，读写方便 | 不便于SQL查询样本明细 |

**选择JSON的理由：**

1. **数据量估算**
   - 每次抽样约400条样本
   - 每个学生3种方法 = 1200条
   - 每个班级40人 = 48000条
   - 每学期10个班级 = 48万条
   - 如果用明细表，数据量增长极快

2. **使用场景分析**
   - 抽样结果主要用于生成图表
   - 图表计算在应用层完成
   - 不需要跨学生查询样本明细
   - 查询都是「取出某学生的全部抽样结果」

3. **JSON结构设计**
   ```json
   {
     "simple_random": {
       "sample_count": 400,
       "sample_data": [...]
     },
     "systematic": {
       "k_value": 25,
       "sample_count": 400,
       "sample_data": [...]
     },
     "stratified": {
       "stratify_field": "性别",
       "allocation": [...],
       "sample_count": 400,
       "sample_data": [...]
     }
   }
   ```

### 3.4 实验记录与提交历史的关系

**决策：experiment记录当前状态，submission记录历史快照**

**设计思路：**

```
学生第一次做实验：
  → 创建experiment记录，状态=进行中
  → 完成后提交
  → 创建submission记录#1，状态=待批改
  → experiment状态改为已提交

教师批改通过：
  → submission#1状态改为已批改，记录分数
  → experiment状态改为已批改

教师驳回：
  → submission#1状态改为被驳回，记录驳回理由
  → experiment状态改为被驳回

学生重做：
  → 清空experiment中的实验数据
  → experiment状态改为进行中，current_stage重置
  → 完成后再次提交
  → 创建submission记录#2
```

**这样设计的好处：**

1. **experiment表**
   - 始终反映学生当前的实验进度
   - 方便查询「进行到哪个阶段」
   - 重做时直接更新，不产生冗余记录

2. **submission表**
   - 保留每次提交的完整快照
   - 支持查看历史提交（问卷PDF、报告PDF）
   - 记录每次批改的分数和评语

### 3.5 批改人记录方式

**决策：使用 type + id 组合字段**

**方案对比：**

| 方案 | 实现方式 | 优缺点 |
|------|----------|--------|
| 两个外键 | graded_by_teacher_id, graded_by_assistant_id | 字段冗余，总有一个为NULL |
| 单一外键 + 类型 | graded_by_type, graded_by_id | 简洁，但需应用层判断 |
| 多态关联表 | 单独建关联表 | 过度设计 |

**选择 type + id 的理由：**

1. 字段简洁，只需两个字段
2. 查询时根据type判断关联teacher表还是assistant表
3. 对于MVP阶段足够使用

**字段定义：**
```sql
graded_by_type TINYINT    -- 1=教师，2=助教
graded_by_id BIGINT       -- 对应teacher.id或assistant.id
```

### 3.6 软删除策略

**决策：仅对课题表使用软删除**

| 表 | 删除策略 | 理由 |
|------|----------|------|
| topic | 软删除 | 已发布的课题删除后学生数据仍需保留 |
| student | 状态字段 | 用status区分正常/停用，非真正删除 |
| 其他表 | 物理删除或级联删除 | 数据依赖关系明确，无需保留 |

## 五、JSON字段结构定义

### 5.1 topic.field_mapping（字段映射配置）

```json
{
  "fields": [
    {
      "name": "性别",
      "type": "stratification",
      "unique_values": ["男", "女"]
    },
    {
      "name": "年龄",
      "type": "numeric"
    },
    {
      "name": "职业",
      "type": "categorical"
    },
    {
      "name": "ID",
      "type": "identifier"
    }
  ]
```

## 七、视图设计

为简化常用查询，设计以下视图：

### 7.1 v_class_student_count（班级学生数量统计）

**用途：** 班级列表页显示学生数量

```sql
SELECT 
    c.id AS class_id,
    c.name AS class_name,
    c.semester_id,
    c.teacher_id,
    COUNT(s.id) AS student_count
FROM class c
LEFT JOIN student s ON c.id = s.class_id AND s.status = 1
GROUP BY c.id, c.name, c.semester_id, c.teacher_id;
```

### 7.2 v_task_progress（任务进度统计）

**用途：** 任务列表页显示完成进度

```sql
SELECT 
    t.id AS task_id,
    t.topic_id,
    t.class_id,
    tp.name AS topic_name,
    c.name AS class_name,
    t.deadline,
    COUNT(DISTINCT s.id) AS total_students,
    COUNT(DISTINCT e.id) AS started_count,
    SUM(CASE WHEN e.status = 1 THEN 1 ELSE 0 END) AS submitted_count,
    SUM(CASE WHEN e.status = 2 THEN 1 ELSE 0 END) AS graded_count,
    SUM(CASE WHEN e.status = 3 THEN 1 ELSE 0 END) AS rejected_count
FROM task t
JOIN topic tp ON t.topic_id = tp.id
JOIN class c ON t.class_id = c.id
LEFT JOIN student s ON c.id = s.class_id AND s.status = 1
LEFT JOIN experiment e ON t.id = e.task_id AND s.id = e.student_id
GROUP BY t.id, t.topic_id, t.class_id, tp.name, c.name, t.deadline;
```

### 7.3 v_pending_submissions（待批改作业）

**用途：** 批改列表页查询待批改作业

```sql
SELECT 
    sub.id AS submission_id,
    sub.experiment_id,
    sub.submitted_at,
    e.student_id,
    s.student_id AS student_no,
    s.name AS student_name,
    t.id AS task_id,
    tp.id AS topic_id,
    tp.name AS topic_name,
    c.id AS class_id,
    c.name AS class_name,
    c.teacher_id
FROM submission sub
JOIN experiment e ON sub.experiment_id = e.id
JOIN student s ON e.student_id = s.id
JOIN task t ON e.task_id = t.id
JOIN topic tp ON t.topic_id = tp.id
JOIN class c ON t.class_id = c.id
WHERE sub.status = 1;
```

### 8.2 应用层约束

以下约束需要在应用层实现：

1. **学期唯一当前**：设置新的当前学期时，需先将原当前学期改为历史
2. **评分权重求和**：三项权重之和必须等于100
3. **提交前校验**：四个阶段都完成才能提交
4. **截止时间校验**：超过截止时间不能提交（除非延期）

## 十、总结

### 10.1 表数量统计

| 分类 | 表数量 | 表名 |
|------|--------|------|
| 用户域 | 4 | admin, teacher, assistant, student |
| 组织域 | 3 | semester, class, assistant_class |
| 教学域 | 4 | topic, topic_attachment, topic_recommend_question, task |
| 实验域 | 2 | experiment, submission |
| 系统域 | 1 | announcement |
| **合计** | **14** | |

### 10.2 设计亮点

1. **用户分表**：四类用户独立建表，字段清晰，权限分明
2. **JSON灵活存储**：问卷、抽样结果等复杂数据用JSON存储，避免表爆炸
3. **历史快照**：submission表保留每次提交的完整快照，支持历史查看
4. **软删除**：课题采用软删除，防止误操作导致数据丢失
5. **视图优化**：提供常用统计视图，简化业务查询

### 10.3 后续优化方向

1. **读写分离**：如果访问量增大，可考虑主从复制
2. **JSON索引**：MySQL 8.0支持JSON字段的函数索引，可按需添加
3. **分表分库**：如果数据量持续增长，可按学期分表
4. **缓存层**：高频查询（如班级列表、任务进度）可加Redis缓存
