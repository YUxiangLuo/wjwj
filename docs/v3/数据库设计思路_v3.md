## 二、设计原则

### 2.1 继承 V2.0 的设计原则

| 原则 | 说明 | 在V3.0中的体现 |
|------|------|----------------|
| 简洁优先 | 避免过度设计 | 锁定字段直接加在业务表，而非单独建锁表 |
| 数据完整性 | 外键约束保证一致性 | 新增表遵循外键规范 |
| 查询效率 | 高频查询字段建立索引 | 会话表的token、通知表的receiver索引 |
| 可扩展性 | JSON字段存储可变结构 | 通知的extra_data字段 |
| 软删除 | 关键数据不物理删除 | 统一使用deleted_at字段 |

### 2.2 V3.0 新增设计原则

| 原则 | 说明 | 应用场景 |
|------|------|----------|
| 统一用户标识 | 使用(user_type, user_id)组合标识用户 | 会话、通知、日志等跨角色表 |
| 乐观锁控制 | 使用version字段防止并发冲突 | experiment表的版本控制 |
| 时间锁过期 | 锁定有过期时间，自动释放 | 批改锁定30分钟自动过期 |
| 配置外置 | 可调参数存数据库而非硬编码 | 锁定时长、超时时间等 |
| 审计追踪 | 关键操作记录变更历史 | 转班记录、密码修改日志 |

### 2.3 用户类型编码规范

为了在跨角色表中统一标识用户，定义用户类型编码：

| user_type | 角色 | 对应表 |
|-----------|------|--------|
| 1 | 管理员 | admin |
| 2 | 教师 | teacher |
| 3 | 助教 | assistant |
| 4 | 学生 | student |

## 三、表结构设计方案

### 3.1 用户域表修改

#### 3.1.1 用户表统一新增字段

为四个用户表（admin, teacher, assistant, student）统一新增登录锁定相关字段：

```sql
-- 新增字段
login_fail_count    TINYINT UNSIGNED DEFAULT 0    -- 连续登录失败次数
locked_until        DATETIME DEFAULT NULL          -- 锁定截止时间（NULL表示未锁定）
```

**设计说明：**
- `login_fail_count`：记录连续失败次数，登录成功后清零
- `locked_until`：锁定截止时间，为NULL表示未锁定，有值且未过期表示锁定中
- 不单独建锁定表的原因：锁定状态与用户强绑定，且字段简单，直接加在用户表更高效

#### 3.1.2 student 表额外修改

```sql
-- 软删除支持
deleted_at          DATETIME DEFAULT NULL          -- 删除时间（NULL表示未删除）
```

**设计说明：**
- V2.0中student表没有软删除支持，V3.0需要支持删除学生但保留数据
- 使用deleted_at而非is_deleted的原因：可以记录删除时间，且NULL/非NULL判断同样高效

### 3.2 新增：会话管理表 (user_session)

```sql
CREATE TABLE user_session (
    id              BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    session_token   VARCHAR(128) NOT NULL,          -- 会话令牌（UUID或JWT）
    user_type       TINYINT NOT NULL,               -- 用户类型
    user_id         BIGINT UNSIGNED NOT NULL,       -- 用户ID
    device_info     VARCHAR(500),                   -- 设备信息（UA、IP等）
    created_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at      DATETIME NOT NULL,              -- 过期时间
    last_active_at  DATETIME NOT NULL,              -- 最后活动时间

    UNIQUE KEY uk_token (session_token),
    KEY idx_user (user_type, user_id),
    KEY idx_expires (expires_at)
);
```

**设计说明：**

| 设计决策 | 方案 | 理由 |
|----------|------|------|
| 为什么单独建表 | 不放在用户表 | 会话是临时数据，有过期和清理需求 |
| 单设备登录如何实现 | 新登录时删除该用户旧会话 | 简单直接，无需复杂逻辑 |
| token 存储方式 | 数据库存储 | 支持服务端主动失效，便于管理 |
| 是否用Redis | 暂不使用 | MVP阶段数据库足够，后续可迁移 |

**会话超时实现：**
- `expires_at`：绝对过期时间，创建时根据角色设置
- `last_active_at`：用于滑动过期（可选），每次请求更新
- 定时任务清理过期会话

### 3.3 新增：通知表 (notification)

```sql
CREATE TABLE notification (
    id              BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,

    -- 接收者信息
    receiver_type   TINYINT NOT NULL,               -- 接收者类型
    receiver_id     BIGINT UNSIGNED NOT NULL,       -- 接收者ID

    -- 通知内容
    type            VARCHAR(50) NOT NULL,           -- 通知类型
    title           VARCHAR(200) NOT NULL,          -- 标题
    content         TEXT NOT NULL,                  -- 内容

    -- 关联信息（可选，用于跳转）
    related_type    VARCHAR(50),                    -- 关联对象类型：task, submission等
    related_id      BIGINT UNSIGNED,                -- 关联对象ID

    -- 状态
    is_read         TINYINT(1) NOT NULL DEFAULT 0,  -- 是否已读
    read_at         DATETIME,                       -- 阅读时间

    created_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    KEY idx_receiver (receiver_type, receiver_id, is_read),
    KEY idx_created (created_at)
);
```

**通知类型枚举：**

| type 值 | 说明 | 触发时机 |
|---------|------|----------|
| TASK_PUBLISHED | 任务发布 | 教师发布任务到班级 |
| TASK_DEADLINE_REMINDER | 截止提醒 | 任务截止前24小时 |
| TASK_DEADLINE_EXTENDED | 截止延长 | 教师延长截止时间 |
| SUBMISSION_GRADED | 批改完成 | 作业被批改通过 |
| SUBMISSION_REJECTED | 作业驳回 | 作业被驳回 |
| ANNOUNCEMENT | 系统公告 | 管理员发布公告 |

**设计说明：**

| 设计决策 | 方案 | 理由 |
|----------|------|------|
| 是否与公告表合并 | 分开 | 公告是一对多广播，通知是点对点 |
| 内容是否存快照 | 是 | 避免关联对象删除后通知内容丢失 |
| related_type/id 用途 | 点击跳转 | 用户点击通知可跳转到相关页面 |
| 保留策略 | 90天自动清理 | 与V3功能描述一致 |

### 3.4 新增：系统配置表 (system_config)

```sql
CREATE TABLE system_config (
    id              BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    config_key      VARCHAR(100) NOT NULL,          -- 配置键
    config_value    TEXT NOT NULL,                  -- 配置值
    value_type      VARCHAR(20) NOT NULL DEFAULT 'string', -- 值类型：string/int/boolean/json
    description     VARCHAR(500),                   -- 配置说明
    updated_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    UNIQUE KEY uk_key (config_key)
);
```

**预置配置项：**

| config_key | config_value | value_type | description |
|------------|--------------|------------|-------------|
| login.max_fail_count | 5 | int | 登录失败锁定阈值 |
| login.lock_duration_minutes | 30 | int | 锁定时长（分钟） |
| session.admin_timeout_minutes | 30 | int | 管理员会话超时 |
| session.teacher_timeout_minutes | 120 | int | 教师会话超时 |
| session.student_timeout_minutes | 240 | int | 学生会话超时 |
| file.excel_max_rows | 100000 | int | Excel最大行数 |
| file.attachment_max_size_mb | 50 | int | 附件最大大小 |
| notification.retention_days | 90 | int | 通知保留天数 |
| grading.lock_timeout_minutes | 30 | int | 批改锁定超时 |

**设计说明：**
- 使用key-value形式而非每个配置一列：灵活，可动态增加配置
- value_type字段：便于应用层正确解析值类型
- 配置可在管理员端修改，无需改代码重启

### 3.5 新增：学生转班记录表 (student_transfer)

```sql
CREATE TABLE student_transfer (
    id              BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    student_id      BIGINT UNSIGNED NOT NULL,       -- 学生ID
    from_class_id   BIGINT UNSIGNED NOT NULL,       -- 原班级ID
    to_class_id     BIGINT UNSIGNED NOT NULL,       -- 新班级ID
    reason          VARCHAR(500),                   -- 转班原因（可选）
    operated_by     BIGINT UNSIGNED NOT NULL,       -- 操作人（管理员ID）
    transferred_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    KEY idx_student (student_id),
    KEY idx_from_class (from_class_id),
    KEY idx_to_class (to_class_id),

    CONSTRAINT fk_transfer_student FOREIGN KEY (student_id) REFERENCES student(id),
    CONSTRAINT fk_transfer_from FOREIGN KEY (from_class_id) REFERENCES class(id),
    CONSTRAINT fk_transfer_to FOREIGN KEY (to_class_id) REFERENCES class(id)
);
```

**设计说明：**
- 记录每次转班操作，支持审计追踪
- 转班后学生的class_id直接更新为新班级
- 原班级的实验数据保留在experiment表中（通过task_id可追溯）

### 3.6 课题表 (topic) 修改

```sql
-- 新增字段
locked_by           BIGINT UNSIGNED DEFAULT NULL,   -- 当前编辑锁定人（教师ID）
locked_at           DATETIME DEFAULT NULL,          -- 锁定开始时间
deleted_at          DATETIME DEFAULT NULL,          -- 软删除时间
```

**编辑锁定逻辑：**
- 教师打开编辑页面时，设置locked_by和locked_at
- 其他教师打开时检查：如果locked_by非空且locked_at在30分钟内，提示被锁定
- 保存或关闭页面时，清除锁定
- 超过30分钟的锁定自动视为无效

### 3.7 任务表 (task) 修改

```sql
-- 新增字段
deleted_at          DATETIME DEFAULT NULL,          -- 软删除时间
```

### 3.8 实验记录表 (experiment) 修改

```sql
-- 新增字段
last_saved_at       DATETIME DEFAULT NULL,          -- 最后自动保存时间
version             INT UNSIGNED DEFAULT 1,         -- 版本号（乐观锁）
```

**乐观锁使用：**
- 每次保存时version+1
- 前端提交时带上当前version
- 后端检查version是否匹配，不匹配说明有并发修改

### 3.9 提交记录表 (submission) 修改

```sql
-- 新增字段
locked_by_type      TINYINT DEFAULT NULL,           -- 锁定人类型（2-教师，3-助教）
locked_by_id        BIGINT UNSIGNED DEFAULT NULL,   -- 锁定人ID
locked_at           DATETIME DEFAULT NULL,          -- 锁定开始时间
```

**批改锁定逻辑：**
- 打开批改页面时，检查是否有未过期的锁定
- 无锁定：设置锁定
- 有锁定（他人）：提示被锁定，只读模式
- 有锁定（自己）：更新锁定时间，继续编辑
- 保存/通过/驳回后清除锁定
- 30分钟无操作自动过期

```sql
CREATE VIEW v_user_unread_notification_count AS
SELECT
    receiver_type,
```

```sql
CREATE VIEW v_active_session_stats AS

    user_type,
```

## 七、数据清理策略

### 7.1 定时清理任务

| 数据类型 | 保留策略 | 清理SQL |
|----------|----------|---------|
| 过期会话 | 即时清理 | `DELETE FROM user_session WHERE expires_at < NOW()` |
| 通知 | 90天 | `DELETE FROM notification WHERE created_at < DATE_SUB(NOW(), INTERVAL 90 DAY)` |
| 登录日志 | 90天 | `DELETE FROM login_log WHERE login_at < DATE_SUB(NOW(), INTERVAL 90 DAY)` |
| 监控数据 | 30天 | `DELETE FROM system_metrics WHERE recorded_at < DATE_SUB(NOW(), INTERVAL 30 DAY)` |
| 操作日志 | 365天 | `DELETE FROM operation_log WHERE created_at < DATE_SUB(NOW(), INTERVAL 365 DAY)` |

### 7.2 清理执行频率建议

| 任务 | 频率 | 原因 |
|------|------|------|
| 过期会话清理 | 每小时 | 实时性要求高 |
| 通知清理 | 每天凌晨 | 数据量适中 |
| 日志清理 | 每天凌晨 | 数据量大，低峰期执行 |

## 九、设计决策说明

### 9.1 为什么不使用单独的锁表？

**考虑过的方案：**
```sql
CREATE TABLE resource_lock (
    resource_type VARCHAR(50),
    resource_id BIGINT,
    locked_by_type TINYINT,
    locked_by_id BIGINT,
    locked_at DATETIME,
    PRIMARY KEY (resource_type, resource_id)
);
```

**最终选择：** 在业务表中直接添加锁字段

**理由：**
1. 锁定场景有限（仅topic编辑、submission批改）
2. 直接在业务表加字段，查询时无需JOIN
3. 锁与业务数据强相关，放在一起更直观
4. 避免引入额外的表维护复杂性

### 9.2 为什么会话不用Redis？

**考虑过的方案：** 使用Redis存储会话

**最终选择：** 使用MySQL的user_session表

**理由：**
1. MVP阶段，系统并发量有限，MySQL足够
2. 减少运维复杂度，无需维护Redis
3. 会话数据需要持久化（审计需求）
4. 后续如有性能瓶颈，可平滑迁移到Redis

### 9.3 为什么通知和公告分开？

**分析：**

| 维度 | 公告 (announcement) | 通知 (notification) |
|------|---------------------|---------------------|
| 发送模式 | 一对多广播 | 点对点 |
| 创建者 | 管理员手动发布 | 系统自动生成 |
| 内容 | 富文本，内容较长 | 简短，有模板 |
| 已读追踪 | 单独表记录 | 内嵌is_read字段 |
| 生命周期 | 长期有效 | 90天后清理 |

**结论：** 差异较大，分开设计更清晰

### 9.4 软删除字段的选择

**考虑过的方案：**
- 方案A：`is_deleted TINYINT(1) DEFAULT 0`
- 方案B：`deleted_at DATETIME DEFAULT NULL`

**最终选择：** 方案B（deleted_at）

**理由：**
1. 可以记录删除时间，便于审计
2. NULL值判断与0/1判断性能相当
3. 与created_at、updated_at风格一致
4. 可支持"回收站"功能（显示删除时间）
