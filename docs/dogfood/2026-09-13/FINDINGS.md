## 二、观察项

### OBS-1 / P3 — 比例样本量规划内部固定假设 p=0.5，且该假设对用户不可见

- **现象**：比例研究的「建议样本量」不随该类别在总体中的实际占比变化。规划请求体中没有期望比例的输入字段，服务端校验也只接受按 `p=0.5` 算出的值。
- **证据**：以 200 行、目标类别实际占比 30% 的比例课题做探测：
  - 用总体实际占比 p=0.3 计算的候选值（124 / 164 / 141）**全部被拒**（错误为「建议样本量与当前规划参数不一致」）；
  - 改用 p=0.5 计算后**逐条吻合**：cl=95%/e=5%/deff=1/r=0 → 132；cl=95%/e=3% → 169；cl=90%/e=5%/deff=1.5/r=0.1 → 150；cl=99%/e=2%/deff=2/r=0.3 → 200（N 封顶）。
- **评价**：p=0.5 是 Cochran 在缺少先验估计时的标准保守做法，**计算本身正确**，不属缺陷。但学生看不到「按最不利情况 50% 计算」这一前提，容易误以为推荐样本量已反映本课题的真实类别比例（如 30%），进而低估所需样本量或误解精度来源。
- **建议**：在规划页明确标注该假设（例如「比例估计在缺少先验比例时按最不利的 50% 计算」），或提供可选的期望比例输入；若提供输入，需同步更新校验与快照口径。
- **未做**：本轮不改产品，仅记录。

## 三、已验证的语义（非缺陷，但重要）
### SEM-1 — 展示的标准误是“设计层”口径，使用已知总体方差

在 N=8 的小总体上，简单随机抽样的标准误为 `sqrt(20) = 4.47213595499958`，而样本估计口径 `sqrt((1-n/N)·s²/n)` 为 `5.8689`。

- 精确匹配的公式是 **`V(ȳ) = (σ²/n)·(N-n)/(N-1)`**，其中 σ² 是**已知总体方差**（84）：`sqrt(84/3 × 5/7) = sqrt(20)` ✓
- 更强的判别证据：**换一个样本后该 SE 完全不变**（4.4721 vs 4.4721，样本从 [7,31,11] 换为 [7,19,31]），而估计量随之变化（16.333 → 19）。样本估计口径不可能有这种不变性。
- 这与 README 的说法一致：「本实验使用完整虚拟总体演示抽样设计，因此可以对照总体真值并计算设计层面的误差」。
- **意义**：课堂上展示的“教学误差半宽”是该完整总体上**设计层面**的误差，真实抽样调查无法算出（因为看不到总体方差），必须用样本估计。若页面已在这一点上给出说明，则无问题；建议持续保持该说明可见，避免学生把它当成可用真实数据复现的量。

### OBS-2 / P3 — 不支持的查询参数被静默忽略（成绩导出接口不对称）

- **现象**：`grade-export/data` 与 `grade-export/excel` 接受 `classId`/`topicId`/`taskId`/`taskIds`/`semester`；而 `grade-export/preview` 与 `grade-export/analytics` **只解析** `classId`/`topicId`/`semester`。传入 `taskId` 既不生效也不报错。
- **证据**：以同一 `taskId` 请求时，`data` 返回 2 行而 `preview` 返回 35 行、`analytics.scores.count` 为 7——后两者实际按整个教师范围聚合。而 `classId` 非法时两者都会返回 400，说明它们确实在校验参数，只是不识别 `taskId`。
- **是否缺陷**：**不是**。前端 `api-client.ts` 中 `getGradeExportPreview` / `getGradeAnalytics` 的类型本就不含 `taskId`，页面也只在导出（data/excel）时传选中任务；三者职责不同（总览 vs 导出），行为自洽。
- **风险**：仅在于后续调用方可能误传 `taskId` 并拿到**偏大**的结果而不自知。建议对不支持的参数显式拒绝或忽略并声明，而非静默。
- **未做**：本轮不改产品，仅记录。

### DG-DF-01 — **已撤销（误报）**：题目编辑器并不强制要求选项

> **二次确认结论：原 P1 判定不成立，予以撤销。** 首轮的错误来自我自己的自动化方式，不是产品缺陷。

**首次判断（错误）**：认为「题目编辑器强制要求选项，导致是/否题与评分题无法创建」。

**二次确认推翻它的三条证据**

1. **源码即是条件渲染**（`src/components/questionnaire/QuestionEditor.tsx`）：
   ```tsx
   {(type === "single" || type === "multiple") && ( /* 选项（2-10个）区块 */ )}
   {type === "boolean" && ( /* 固定「是」「否」两个选项 */ )}
   {type === "scale" && ( /* 常用评分预设 */ )}
   ```
   选择 boolean/scale 时选项区块应当**卸载**；首轮却观察到它仍在，说明“题型根本没切过去”。

2. **点击方式决定了结果**（同一对话框，逐项读取 `data-state` 与描述段落）：
   | 操作 | 是/否题 `data-state` | 描述段落 | 选项区块 | 保存 |
   | --- | --- | --- | --- | --- |
   | 初始 | inactive（单选题 active） | 从多个选项中选择一个 | 显示 | 禁用 |
   | **JS `.click()`** | **仍 inactive** | **未变** | 仍显示 | 仍禁用 |
   | **真实鼠标点击** | **active** | 固定「是」「否」两个选项 | **消失** | — |
   → **JS 注入的点击不会激活 Radix Tabs 触发器**，这是我首轮的仪器错误。

3. **真实点击后功能完全正常**：
   - 是/否题 + 只填题干 → `optionSection:false`、`saveDisabled:false` → 保存后题量 0 → **1**（加入成功）；
   - 评分题 + 只填题干 → `optionSection:false`、`scaleSection:true`、`saveDisabled:false`。

**根因（我的）**：首轮用 `document.querySelector(...).click()` 派发合成点击，并在读取“当前题型描述”时用了过于宽松的选择器（`p,span,div` + 正则），把 **TabsTrigger 的标签**误读成描述段落，从而得出“切换生效但选项区仍在”的错误结论。实际是“切换从未生效”。

**教训（已纳入本轮纪律）**：涉及 Radix 等自管理焦点/指针语义的控件，**验证必须用真实指针事件**（agent-browser 的 `click`），不能用 JS `.click()`；读取状态要优先用 `data-state` 等结构化属性，而不是匹配可见文本。

**证据**：`screenshots/student-walkthrough/12-reconfirm-boolean-scale.png`

### DG-OBS-03 / P3 —— sticky 页头遮挡（**二次更正：从 P2 降回 P3**）

> 本条经历了一次升级与一次更正，两次都由我提出，最终结论如下。

**事实（实测）**

| 项 | 值 |
| --- | --- |
| 全局页头 | `sticky top-0 z-50`，0–65px，**背景不透明** `rgb(18,58,99)` |
| 阶段标签栏 | `sticky top-16 z-40`，固定后位于 64–161px，**背景不透明** `rgb(243,246,250)` |
| 两者合计 | 滚动后占用 **161px**：900px 视口占 **18%**、800px 占 **20%**、633px 占 **25%** |
| 根因位置 | `src/components/WorkspaceShell.tsx:38`（全局页头）与 `src/student/pages/ExperimentLayout.tsx:206`（阶段标签栏） |

**为什么最终判 P3 而不是 P2**

1. **被遮挡的控件是完全不可见的**，不是“可见但点不到”。两级 chrome 都是不透明背景，控件落入其区间时整体被盖住；学生看不到就不会去点，滚动一下即可见——符合正常 sticky 页头行为。
2. **应用不会把内容程序化地停在 chrome 之下**：全仓库只有 `ExperimentLayout.tsx:178` 的 `window.scrollTo({top: 0})` 与沉浸式规划自身的 `root.scrollTop = 0`，**没有 `scrollIntoView` 锚点跳转**（已 grep 确认）。因此不存在“点了跳转却跳到遮挡区”的真实路径。
3. 我此前的“学生会以为按钮坏了”缺少依据：既然控件不可见，就没有“点了没反应”的体验。我先前的 P2 升级**依据不成立，予以撤回**。

**仍然值得记录的客观成本（P3）**

在本身就需要大量滚动的问卷编辑页上，两级不透明 sticky chrome 会长期占用约 18%–25% 的视口高度。这是设计取舍，不是缺陷；若后续要优化，可考虑：

- 给滚动容器补 `scroll-padding-top`（收益有限：当前没有 `scrollIntoView` 调用）；
- 滚动时收窄阶段标签栏（例如只保留阶段名，隐藏细项），把占用压到 ~64–80px。

**先前两次判断的更正说明**

- 首轮记为 P3，理由是“按钮会在某滚动区间内失效”；
- 二次确认后我升级为“建议按 P2”，理由是“可能卡住必做步骤（开始受访者视角试填）”；
- **本次更正撤回升级**：该按钮被遮挡时同样完全不可见，且滚动即恢复；`scrollIntoView` 也不存在于产品路径中。**最终维持 P3**。

**证据**：`screenshots/student-walkthrough/13-obs03-realclick.png`、`05-stage1-questionnaire.png`、`06-stage1-questions.png`

**测试侧说明（非产品问题）**：最初用“轮流点候选答案直到通过”的脚本推进，通过两个因素后失效（选择器重复命中已试选项、`检查答案` 引用随重渲染失效）。改为**按题面查表作答**（正确索引取自 `learning.ts`）后一次走完六个因素。

### 学生走查 · 阶段 2 第 4–6 步记录

**第 4 步 理解推荐（用当前数据算一遍）** —— 先展示本任务规划依据（σ² = 173.854、均值口径、“结果为有限总体下的近似规划精度”），再给一道理解检查（“抽取总体中较大一部分单位时，为什么要做有限总体校正？”→“因为已覆盖更多总体单位，剩余的抽样不确定性更小”）。答对后「继续：调整方案」解锁。

**第 5 步 调整方案（把精度要求变成可执行的方案）** —— 左侧目标与假设、右侧实际样本量，改动即时更新预期精度。控件：置信水平 95% (Z=1.96)、绝对误差限 ±2（可输入，min 0.01）、设计效应 1.0（Radix 滑块）、无回答率 0%（Radix 滑块）、最终样本量 45（min 1 / max 60，建议值 45，另有「采用建议值」）、以及只读的「当前选择的预期精度」。

**已独立复算通过**（与学生屏幕上显示逐位一致）：

| 最终样本量 n | 页面显示预期误差限 | 我的独立复算 `1.96·sqrt((173.854/n)·(60−n)/59)` | 页面判定 |
| ---: | --- | --- | --- |
| 45 | ±1.94 | 1.9425 | 预计达到目标 |
| 40 | ±2.38 | 2.3794 | **预计未达到目标** |

即：**改动即时联动、达标/未达标判定正确、且用的是有限总体校正口径**（与 DG-N 的设计层 SE 结论一致）。

**未验证（NOT_RUN，不得计入通过）**：无回答率滑块对“建议样本量/邀请数”的放大（预期应为 邀请数 = n ÷ (1−r)）。该滑块是 Radix 控件，我用 `focus()` + 方向键与 `mouse down/move/up` 两种方式均未改变其 `aria-valuenow`（我取到的“轨道”实为宽仅 20px 的 thumb 包装层，未定位到真实轨道）。**底层公式本轮 DG-N 已用独立 oracle 验证**，故此处只是 UI 交互未确认，不记为缺陷。

**第 6 步 快速自检（不计分、可重试）** —— 三个问题串起精度、总体规模与抽样设计：`ME = Z × SE`、总体 2,000→200,000 时比例规划样本量“从约 322 增到约 384，增加约两成”、`deff = 2` 的含义。第 1 题作答正确并出现「下一题」，已推进到 **2 / 3**。第 2 题我的自动作答未生效（引用失效），**第 6 步整体尚未完成、规划尚未保存**。

### 阶段 3 抽样执行 —— 已验证

执行了必做方法（简单随机）与系统抽样，满足页面要求「至少完成两种方法」。

**简单随机（必做）**

**系统抽样（选做）**
- 页面：「K=1.3333，共抽取 45 个样本，耗时 42 ms」。
- **独立复算逐项一致**：以 `randomStart=1.241975494970878`、`K=60/45` 按 `floor(randomStart + i·K)`（i=0..44）生成的 45 个索引与产品**完全相同**（`JSON.stringify` 全等）；另一种常见实现 `start + floor(i·K)` 则不一致——即产品采用的是「浮点起点 + 取整」的等距实现。间隔序列呈 `1,1,2` 循环，正是 K=4/3 的特征。
