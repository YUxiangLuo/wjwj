# 账号体系 Review（班级管理 / 用户导入）

范围：学生与教师账号的创建、导入、停用、删除、班级归属，以及班级/学期的生命周期。
动机：历史上出现过「软删除导致学生永远无法重新导入」，本轮对该类问题做系统排查、修复与回归测试。

## 1. 数据模型与硬约束

| 实体 | 关键约束 | 含义 |
| --- | --- | --- |
| `student` | `student_id` **citext UNIQUE（全表）**，`class_id` NOT NULL | 学号全局唯一，且一个学生同时只能属于一个班级 |
| `student.status` | `smallint` 0/1 | 0 = 停用（软删除），行保留 |
| `teacher` | `employee_id` citext UNIQUE，无删除接口 | 教师只能停用，工号永久占用 |
| `class` | 硬删除；有学生（含停用）或任务时拒绝 | 班级可被管理员删除 |
| `semester` | 当前学期不可删；有班级时拒绝 | — |
| `experiment.student_id` | `ON DELETE CASCADE` | 硬删学生会级联删除实验/提交/成绩/抽样记录 |

关键推论：**停用（status=0）不会释放学号**。任何"按学号查重"的逻辑只要忽略 `status`，就会把停用账号变成永久死锁——这正是历史缺陷的根因。

## 2. 生命周期状态机

```
（不存在）--导入/新增--> 活跃(status=1) <--启用-- 停用(status=0)
                          |                          |
                          +--------禁用--------------+
                          |
                          +---硬删除---> （行消失，学号释放，实验/成绩级联删除）
```

- 教师：`不存在 → 活跃 ⇄ 停用`（无删除）。
- 班级：`不存在 → 存在`（有学生/任务即不可删）。
- 学期：`存在 → 删除`（当前学期/有班级不可删）。

## 3. 风险清单

| # | 风险 | 严重度 | 处置 |
| --- | --- | --- | --- |
| R1 | 停用学生后无法重新导入：导入/新增按学号查重时不看 `status`，报「学号已存在」且无任何可行操作提示 → 教师只能永久删除（丢失全部成绩）或放弃 | **高** | ✅ 已修复 |
| R2 | 学号被**其他班级**占用时报错不说明归属，教师无从下手；跨教师时又可能泄露班级名 | 中 | ✅ 已修复 |
| R3 | 导入到停用账号上无"恢复"语义，无法把名单恢复为当前学期名单 | 中 | ✅ 已修复（原地启用，保留原密码） |
| R4 | 导入并发（同一学号多请求）可能触发唯一约束 → 500 | 中 | ✔ 实测已由全局冲突映射兜底为 409 `CONFLICT` |
| R5 | 硬删除学生静默级联删除实验/提交/成绩/抽样记录 | 中 | ⚠ 保持现状（UI 已明确告知"永久删除…不可恢复"），见 D2 |
| R6 | 学生无法转班：`class_id` NOT NULL + 学号全局唯一，转班只能"删除+重建"，历史随之丢失 | 中 | ⏳ 待决策 D1 |
| R7 | 班级列表「学生数」只统计活跃学生，停用学生不可见；班级因停用学生无法删除时提示笼统 | 低 | ✅ 已修复（`disabledStudentCount` + 删除原因含停用数） |
| R8 | 管理员新建教师遇停用工号时提示「工号已存在」，不说明账号存在但已停用 | 低 | ✅ 已修复 |
| R9 | 重新导入活跃账号会覆盖姓名/邮箱？ | 低 | ✅ 明确为"跳过不改写"（`skippedCount`），并有回归测试固定该语义 |
| R10 | 停用教师仍有班级 | 低 | ⏳ 待决策 D4（当前仅能停用，班级仍可被管理员移交） |

## 4. 修复内容

**导入/新增的学生账号分类处理**（`src/teacher/routes/classroom.ts`）
按学号查到已有账号后，结合「班级归属 + 教师归属 + 状态」四类处理：

| 情况 | 行为 |
| --- | --- |
| 不存在 | 新建（密码=学号），计入 `successCount` |
| 本班 + 活跃 | 跳过不改写，计入 `skippedCount`（不再算失败） |
| 本班 + 停用 | **原地启用**（`status=1`，按名单更新姓名；名单有邮箱才覆盖），计入 `restoredCount`，**保留原密码** |
| 其他班 + 同教师 | 失败，提示 `学号已存在于班级「X」，如需变更班级请先在该班级删除该学生` |
| 停用 + 其他班（同教师） | 失败，提示该班已停用，需先在该班启用或删除 |
| 其他教师 | 失败，提示「学号已被其他教师使用」（**不含班级名**，避免跨教师信息泄露） |

- 启用写入带 `status=0` 谓词，并发启用/删除时不会被陈旧名单覆盖。
- 导入结果新增 `restoredCount` / `skippedCount` / `restored` / `skipped`，前端对话框分别展示"新建 / 重新启用 / 已存在跳过 / 失败"，并说明重新启用保留原密码。

**其他**
- 班级列表新增 `disabledStudentCount`，班级管理页对停用学生显示「另 N 名已停用」。
- 班级删除失败提示具体原因，例如「班级已有 5 名学生（其中 2 名已停用，需先从名单中删除）、1 个任务，无法删除」。
- 管理员新建教师遇停用工号时提示「工号已存在且账号已停用，请在教师列表中重新启用该账号」。

## 5. 测试覆盖

单元/路由（`bun test --isolate src scripts`）新增 10 条：
- `classroom-import.route.test.ts`：新增已停用账号原地启用、名单缺邮箱时保留原邮箱、活跃重复跳过、以及三类冲突（本班外/停用他班/其他教师）提示与"不泄露他人班级名"。
- `classroom-class-list.route.test.ts`：停用学生单独计数，不计入活跃分母。
- `management-account-duplicates.test.ts`：管理员建教师遇停用/活跃重复的两条提示。

真实数据库集成（`bun run test:db`）新增 2 条：
- `a disabled student can be re-imported and is reactivated in place`：真实走「新增 → 停用 → 重新导入」，断言只存在一行、学号不变、密码保留、**学生可再次登录**。
- `re-importing an active roster row neither duplicates nor rewrites the account`：活跃重复不新增、不改名、不改密码。

浏览器实测（教师端）：新增学生 → 界面禁用 → 上传名单导入 → 对话框显示「新建 0 条 / 重新启用 1 条 / 失败 0 条」与逐行「已重新启用」，学生回到「正常」；班级列表停用计数同步变化。

## 6. 待决策

- **D1 转班**：是否提供"学生转班"操作（改 `class_id`、保留账号与历史）？当前只能删除后重建，代价是清空实验/成绩。
- **D2 硬删除保护**：是否在存在已提交/已批改实验时禁止硬删除（改为必须停用），或要求显式 `force` 二次确认？当前级联删除且仅 UI 文案告知。
- **D3 活跃账号名单同步**：重新导入是否应更新活跃账号的姓名/邮箱（"名单即事实"），还是保持"跳过不改写"？
- **D4 教师停用**：是否在有班级时给出明确提示/阻止，避免出现无人可登录的班级？
